# Что ещё проверить на форме авторизации

Пункт 4 задания. Сценарии сгруппированы по областям; **P1** — проверить в первую очередь,
**P2** — важно, **P3** — желательно. Уже автоматизированное отмечено ✅.

## Найдено при исследовании формы

| # | Что | Где | Серьёзность |
|---|---|---|---|
| 1 | После неудачного входа сервер возвращает введённый пароль в HTML: `<input type="password" … value="…">`. Пароль виден в исходном коде страницы, может осесть в кэше браузера или прокси и в сохранённых копиях страницы. | `POST /login` | Средняя (безопасность) |

Воспроизведение автотестом: `vendor/bin/codecept run Acceptance -g known-issues`.
Исправление — как в шаблоне Yii2 advanced: перед повторным рендером формы очищать поле,
`$model->password = '';` в `SiteController::actionLogin()`.

## Вход

- ✅ Невалидные логин/пароль, некорректный формат email, пустые поля, поля из пробелов
- P1 Вход валидной учёткой, редирект на рабочий стол; `/login` для уже вошедшего пользователя редиректит внутрь
- P1 Возврат на изначально запрошенную страницу после входа (`returnUrl`), в том числе защита от открытого редиректа на внешний домен
- P1 Email в другом регистре и с пробелами по краям — вход проходит; пароль не обрезается и чувствителен к регистру
- P1 Учётка в статусах «заблокирована», «не активирована», «удалена» — вход запрещён, сообщение не раскрывает статус постороннему
- P1 Пользователь другого брендового портала (портал мультибрендовый, у каждого бренда свой поддомен) не входит на этот
- P2 Отправка по Enter из любого поля; двойной клик по «Войти» не шлёт два запроса
- P2 Выход из системы: кнопка «Назад» в браузере не возвращает в CRM, сессия недействительна
- P2 Граничные длины: email и пароль по 255 символов, длиннее — понятная ошибка, а не 500
- P3 Пароль с юникодом, эмодзи и спецсимволами; email с `+`, с поддоменом, IDN-домен

## Безопасность

- P1 Перебор паролей: после N неудачных попыток — задержка, капча или временная блокировка (по учётке и по IP)
- P1 Одинаковый ответ и примерно одинаковое время ответа для «нет такого email» и «неверный пароль» — нельзя перебрать существующие адреса
- P1 CSRF: `POST /login` без `_csrf` или с чужим токеном отклоняется (400)
- P1 После входа меняется идентификатор сессии (защита от фиксации сессии)
- P1 Cookie сессии с флагами `HttpOnly`, `Secure`, `SameSite`
- ✅ SQL-инъекция в пароле отклоняется сервером, в логине — клиентской валидацией email
- P1 SQL-инъекция в логине в обход клиентской валидации (прямой `POST /login`)
- P2 XSS в email (`"><script>…`) после ответа сервера возвращается экранированным
- P2 Только HTTPS: `http://` редиректит на `https://`, есть HSTS
- P2 Защита от встраивания в iframe (`X-Frame-Options` или `CSP frame-ancestors`)
- P2 Страница входа и ответ на неудачный вход — с `Cache-Control: no-store`
- P3 Пароль не попадает в URL, логи и аналитику; форма всегда уходит методом POST

## Маскировка и поле пароля

- ✅ Поле `type="password"` при вводе и после ответа сервера
- P2 Пароль нельзя скопировать из поля (Ctrl+C даёт пустоту или точки)
- P3 Корректные `autocomplete="username"` / `autocomplete="current-password"` для менеджеров паролей

## Восстановление пароля

- ✅ Ссылка «Забыли пароль» ведёт на `/site/restore-password`, форма и капча на месте
- P1 Одинаковый ответ для существующего и несуществующего email
- P1 Неверная, пустая и повторно использованная капча отклоняются; капча обновляется по клику
- P1 Ссылка из письма одноразовая и с ограниченным сроком жизни; старый пароль после смены перестаёт работать
- P2 После смены пароля завершаются остальные активные сессии пользователя
- P3 Со страницы восстановления есть понятный путь обратно ко входу

## Интерфейс и доступность

- P2 Переключатель РУС/ENG: все подписи и тексты ошибок переведены, введённые данные не теряются
- P2 Ошибка под полем исчезает, как только поле исправлено; фокус переходит на первое поле с ошибкой
- P2 Навигация с клавиатуры: порядок Tab email → пароль → «Войти» → «Забыли пароль»; метки связаны с полями (`for`)
- P2 Кроссбраузерность (Chrome, Firefox, Safari, Edge) и мобильная вёрстка; для устаревших браузеров показывается предупреждение
- P3 Экранные дикторы озвучивают ошибки (`aria-invalid` уже есть, нужен `aria-describedby` или live-регион)

## Надёжность

- P2 JS-проверка антибота (ServicePipe) не ломает форму и не зацикливается; без JavaScript — внятная заглушка
- P2 Медленная сеть, таймаут или 5xx бэкенда — понятное сообщение, форма не зависает, данные не теряются
- P3 Истёкшая сессия или CSRF-токен (форма долго открыта) — повторная отправка работает, а не падает с 400
